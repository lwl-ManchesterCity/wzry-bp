## 3. 架构：一条硬分界线

这个项目最核心的设计约定：**程序算事实，大模型只负责解释。**

```
shared/            前后端共用纯函数（无 DOM、无 Node API）
  lanes.mjs        五路整体求解 solveLineup（主路100/副路55/第三路30/未列出6）
  styles.mjs       六种执教思路 + 按系列赛序号轮转
        ↓
server/            所有"算"的部分
  index.mjs          唯一入口：三接口 + 事实块拼装 + prompt + 复盘校验   811 行
  synergy.mjs        组合协同推导 + 阵容结构聚合 deriveCombos/analyzeTeam/summarizeStructure
  matchup.mjs        五轴对局模型 + 逐路对位
  composition.mjs    体系闭环度（七环节）+ 胜利路径 + 版本强度使用策略   375 行
  meta-strength.mjs  版本强度（出场×胜率 → 0-100 分，T0-T3）   127 行
  team-planner.mjs   整队规划：束搜索构造五人阵容 + 打分 + BP 决策
  ai-draft.mjs       AI 单步禁选：调 team-planner 定名次，再交给模型
  candidate-view.mjs 把 AI 候选池转成界面可读结构（排序/去重/标注命中）
        ↓
src/               前端
  composables/useDraft.ts   BP 主状态机（系列赛种子、思路序号持久化）
  components/ReviewModal.vue 复盘弹窗（五轴/闭环/胜利路径/版本强度结构化展示）  490 行
  components/LineupBoard.vue 分路拖拽面板
```

**关键行号（省得你全文翻）：**

| 位置 | 干什么 |
|---|---|
| `server/index.mjs:373` `buildMatchupBlock()` | 把分析结果拼成给模型的事实块，每个块带 `factKey` |
| `server/index.mjs:507` `collectFactKeys()` | 白名单：模型只能引用这里面的编号 |
| `server/index.mjs:691` `/api/review` | 复盘主流程，prompt 在 `723` 行 |
| `server/index.mjs:543` `/api/ai-draft` | AI 禁选，prompt 在 `632` 行 |
| `server/synergy.mjs:340` `summarizeStructure()` | 阵容结构聚合，所有阈值的数据源 |
| `server/composition.mjs:242` `judgeComposition()` | 七环节判定，返回 `{passed, total, tier, checks, missing, paths}` |
| `server/composition.mjs:120` `judgeWinPaths()` | 三条胜利路径判 open/contested/blocked |
| `server/composition.mjs:317` `metaUsagePolicy()` | 版本强度什么时候能影响胜负 |
| `server/candidate-view.mjs:17` `toCandidateView()` | 候选池 → 前端展示结构 |

**factKey 白名单机制不要动。** 模型引用了白名单外的编号，前端会标「未引用事实」。这是让 AI 复盘不瞎编的核心手段——它逼模型只能说程序算出来的东西。

## 4. 已经定下来的算法口径（别随手推翻）

这五条都是跟原作者来回争论后定的，每条背后都有具体事故。改之前先读第 5 节的坑。

**① 五轴里只有团战轴带结构加减，其余四轴是求和归一化。**
`matchup.mjs:187`：`raw / (AXIS_MAX[key] * 5) * 100`。线上 / 小规模团战 / 支援 / 推进四轴把五个人的属性加起来算总分；团战轴在求和之上再叠 `teamfightShape()`（`matchup.mjs:59`，叠加处 `matchup.mjs:176-178`）的环节加减：有先手时有人接火 +8、没人接火 −8，输出核心有保护 +6、没人保护 −8，没有 front≥3 的承伤点 −6，单一伤害类型 ≥4 人 −6，结论以 `blueShape/redShape` 注释随轴给出（`matchup.mjs:207`）。所以「能不能自洽」在团战轴里已有分量，但只是这四个加减项，强势期、成型协同、胜利路径三件事五轴完全不碰。**完整的七环节闭环判定只在 `composition.mjs`——不要试图靠调五轴权重或往 teamfightShape 里塞环节解决体系问题，那是加不出来的。**

**② 体系闭环度用「成立几个环节」，不用加权总分。**
七个环节（承伤 / 先手 / 保护 / 伤害类型 / 强势期 / 成型协同 / 胜利路径），每项只判有或没有，`passed` 是计数不是分数。差 2 个环节以上激活「体系优先」，此时落后一方的线上优势只能写成「局部领先」，不能判整体优势。

**③ 版本强度是条件性输入，不是权重项。**
`metaUsagePolicy(closureGap, sampleReady)`：体系差 ≥2，或任一方有效样本不足 3 人（`meta-strength.mjs:29` 的 `MIN_SAMPLE`，取自单侧样本数分布的 p25/p50=3），`diagnosticOnly = true`，版本强度只能进强弱项说明，**不得进 keyFactors、不得改 verdict**；两个条件都不触发才可作平手裁决。样本不足时 `compare()` 的 `leader` 一律 `even`，差值只作诊断。
理由：版本强度（出场×胜率）本质是「哪些英雄进了能赢的阵容」的聚合结果，和闭环度量的是同一件事的不同层级。硬让聚合值去否决本局的直接测量，是在重复计算同一份信息。

**④ 胜利路径分两层判：自己够不够格 → 对方解不解得掉。**
三条路：正面团战、推进拆塔、单抓分带。阈值不是拍的，是 133 英雄随机抽 5 人跑 2 万组取的分位：清线 p50=9/p75=10、推进 p50=6/p75=7、绕后 2 人 p50、机动均值 p50=1.8，门槛定在 p75 附近。

**⑤ 0 场英雄记「无样本」，不给低分。**
新英雄刚进池子也是 0 场，按弱处理会误伤阵容。这是写测试时踩到的。

## 5. 真实踩过的坑（照着这个避）

| 现象 | 根因 | 正确做法 |
|---|---|---|
| 数据文件 diff 虚增 3200 行 | 用 `JSON.stringify` 重写过 JSON，数组炸成一行一个元素，`traits` 键序从「按分路分组」变成「按数值升序」 | **不要用 JSON.parse+stringify 改这两个文件**。`105`/`581` 这种数字字符串当对象键时 JS 强制按数值升序枚举，保不住原顺序。要改就文本级编辑，保持单行数组格式 |
| 团战判「被封死」判反了 | 最初写「对方前排厚 2 点即封死」，导致前排 6 打 8 的一方被判三条路全封、对手反而占优——但对手自己都打不了团 | 按**同一套指标比通过数**，且和闭环度共用 `teamfightParts()` 一个函数，避免两套尺子打架 |
| 保护链模板误套到无位移射手 | 门槛太松，莱西奥被当成保护链受益者 | 收紧为 `peel≥2 + dps≥3 + 机动≤1`，另加「封挡接输出」（`peel≥3 + dps≥3`）单列 |
| 「保核心」思路选出双游走 | 思路分没按出场名额折算 | 思路分要按该英雄在阵容里实际占位折算 |
| 禁人时误用选人加分 | 同一套 evaluate 两种情况复用 | 禁人时不计结构补强/补位加分，排序改 `impact*8 + adjusted*0.25` |
| 禁人面板里同一套阵容显示成两条 | 名单顺序不同导致拼接的 key 不同 | `planKeyOf` **先排序再拼**，再按 key 去重 |
| 同一对英雄两条协同串台 | `synergyNotes` 按英雄对匹配，一对多时错位 | 按**组合名**匹配 + 已用集合去重 |
| 元流之子先选占对抗路，司空震被丢弃 | 分路是「主路先到先得」 | 改成五路整体求解 `solveLineup`，外加手动拖拽兜底 |
| 模型把内部编号写进正文 | prompt 只说「引用事实」，没说「别把编号念出来」 | 正文禁编号、编号只放 `factKeys`，已在 prompt 明确约束（`meta.`/`closure.` 也一并禁） |
| 版本强度算出来和直觉相反 | 以为某阵容版本占优，实算 58 : 74，因为对手拿了 T0 曹操（93）和沈梦溪（84） | 别用印象判断强弱，先跑 `npm run` 下的分析脚本看 `scoreOf` 的实际分值；也别忘了 0 场是「无样本」不是「弱」 |

**还有一个环境坑：** 跑测试时如果看到 exit code 143，那是主动 kill 旧进程的信号，不是测试失败。

## 7. 已知限制（不是 bug，是没做）

- 组合库与宏观七维是**按英雄机制人工标注**，不是官方数据。理解不同就改 JSON
- 赛季数据是快照，手动 `npm run stats:fetch` 才更新；出场不足 15 场参考价值有限
- 五轴分值是相对量，能横向比阵容，不能跨对局纵向比
- 分路对位只按主路落位，副路不自动补位
- AI 是程序化权重（版本强度 / 组合协同 / 临场针对），不是真的战术板推演
- BO3 以上的「留人 / 藏招」没做，系列赛只按序号轮转思路
- BO7 的人机完整路径没跑通
- 复盘弹窗里看不到「AI 当时为什么这么选」的历史，候选池只显示上一手
- 记录不持久化，关页面就没（只有 AI 思路轮转序号存在 localStorage 的 `wzry-bp-series-index`）
- 移动端未适配

## 8. 剩下的活（按价值排序）

**P0 · BO3 以上系列的留人 / 藏招。**
目前每一局都是独立 BP，只有执教思路按系列赛序号轮转。真要像 KPL，得让 AI 记得「上一局已经用过哪套体系」「这局要不要藏一手到第 4 局」。改动会碰 `useDraft.ts` 的系列赛状态和 `styles.mjs` 的轮转策略，先定语义再动手。

**P1 · BO7 人机完整路径。**
代码里有 BO7 选项，但没跑通过完整一局。先 `npm run test:ai` 看它在哪一步断，再决定是补状态还是补 UI。

**P2 · 复盘弹窗补 AI 选人历史。**
候选池只显示上一手。要做就把每手的 `toCandidateView()` 结果随对局存进系列赛记录，复盘时逐手展开。跟 P3 一起做更划算。

**P3 · 记录持久化。**
整轮系列赛记录只存内存，刷新就没了。localStorage 或 IndexedDB 都行，导出 JSON 的入口已经有。模型层不需要改。

**P4 · 移动端适配。** 界面按桌面大屏设计的，窄屏会挤。

**不建议做的：** 重写五轴模型（口径刚标定完）、换掉 factKey 机制（这是防幻觉的核心）、给 AI 加「像人」的随机性（已做过候选洗牌 + 同分抖动，再加就不可复现）。也**不要**自己拍一个权重把复盘判定往「更悬殊」的方向推——判定从 42:58 一路标到 60:40 是靠修正口径得来的，不是靠调系数。
